Deterministic AI Booking Agent: Bringing Conversational Shuttles to Production Scale

Employees book, cancel and track shuttles in plain language on Teams / Slack / WhatsApp — and it feels as fast as the app.

The problem

A naive agent that lets the LLM drive the whole workflow does 5–7 serial inferences per booking — 3–10× slower than tapping through the UI, token-hungry, and liable to call tools out of order in a flow that allocates seats and takes payment.

The insight

The booking flow is a graph we already know — it's literally the UI's screen sequence. So the graph is deterministic code and the LLM does only what it's good at: interpreting messy language and phrasing the reply. The happy path is one small-model NLU call per turn, then parallel REST, then a templated answer.

Tool layer

The Shuttle REST APIs are wrapped as typed tool definitions, each explicitly classified read or write. Reads (get_shifts, get_routes, holidays/cutoffs, check_existing_booking) fan out in parallel; writes (create_booking, cancel_booking, payment) only fire through the guardrail gate below. A response simplifier strips verbose API JSON before it ever reaches the model context, cutting tokens.

Scale & extend

Pods are stateless with all conversation state in Redis — horizontal scale on Kubernetes with an HPA. New capabilities drop in as capability packs behind an intent router. If the LLM is slow or down, it degrades to a zero-inference menu UX; the app is always the escape hatch.

Guardrails — the specific things that stop a bad write

Enforced in code by the flow engine, not by a prompt instruction — so they hold even when the model is wrong.

  • Confirmation gate on every write. create_booking, cancel_booking and payment never execute without an explicit "yes" and all required slots present. Even the one-tap "book my usual" fast path re-confirms — there is no silent auto-booking.
  • Deterministic, templated confirmations. The summary a user approves is template-rendered from the API result, not LLM-generated — so the exact text that gates a write can't be hallucinated or drift.
  • Idempotency on writes. A session-scoped idempotency key on create_booking (paired with a check_existing_booking read) means a retry or double-tap never double-books.
  • Tenant isolation. Every tool call carries the injected BUID, enforced server-side by a BuidInterceptor. Tenant identity never enters the model context, and no PII or internal IDs are echoed back to the user.
  • Scope limiter. Off-domain requests resolve to an OUT_OF_SCOPE intent and get a polite decline instead of an improvised answer.
  • Structural loop prevention. The deterministic engine can't infinite-loop — there is no LLM-driven tool selection on the hot path — and the rare open-ended ReAct fallback keeps a hard step cap.
The reusable lesson: in a latency-sensitive, money-or-seat-allocating flow, don't use the LLM as the workflow engine. Deterministic code for what happens next; the model for understand this utterance and say it nicely.
